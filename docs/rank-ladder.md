# 积分榜速查(src/tools/rank)

工具 code:`rank` · 路由 `#/rank` · 栏目:参考资料 · 徽章:小工具

官方**玩家端小程序**积分排行榜的只读查询台。首屏一次请求出前 200 名，之后下滑无限滚动逐批追加；支持按昵称 / uid 模糊搜索、按段位多选筛选。**不需要登录、不使用 token、不写任何数据。**

入口:首页「小工具」那一排的「积分榜速查」。它按设计**不进侧边栏**(`inNav` 未开),与「结算链推演」同级。

> 本文件是**实测口径的唯一依据**。本仓库不复制那一份反编译档案(它在 `wxappUnpacker` 仓库),只记录结论与它对不上的地方。照档案写代码会踩坑 —— 见下一节。

---

## 1. 接口(实测 2026-10-01,匿名)

```text
POST https://lol-api.playloltcg.com/xcx/userIntegral/ranking/list
Content-Type: application/json
(无任何鉴权头)

{ "pageNum": 1, "pageSize": 200 }
```

响应信封:

```jsonc
{
  "result": [ /* 行数组 */ ],
  "resData": null,
  "code": 0,
  "type": "success",
  "message": "操作成功",
  "timestamp": 1790846443,
  "traceId": "128a613a-cf22-44d4-ac26-3b5c17271d96"
}
```

行的 7 个字段(1000 行样本中**无一为空**):

| 字段 | 类型 | 说明 |
|---|---|---|
| `ranking` | number | 名次。**并列跳号**:1000 行样本的末位是第 996 名,最大并列 32 人 |
| `totalIntegral` | number | 积分 |
| `rankIcon` | string | 段位图标,`cdn.playloltcg.com` 绝对 URL |
| `rankName` | string | 段位名,**服务端直接返回** |
| `uid` | string | 10 位定长字符串;可作列表 key |
| `avatar` | string | 头像,CDN 绝对 URL |
| `name` | string | 昵称 |

段位体系(实测的积分边界,同一 `rankName` 对应唯一图标):

| 段位 | 积分区间 | 1000 行样本中的行数 |
|---|---|---|
| 最强王者 | 1600 – 4120 | 174 |
| 傲世宗师 | 1300 – 1590 | 113 |
| 超凡大师 | 1000 – 1290 | 248 |
| 璀璨钻石 | 720 – 990 | 465 |

**接口不给的东西**(也是刻意的设计边界):没有 `total` / `pages`,没有 `sameRankingCount`,没有 `isMe` / `gender` / `rankChange`。分页只能靠「不足一页即到底」判断。

## 2. 实测修正:与反编译档案对不上的地方

档案里 4 条**反推**结论经真机请求后需要改。前两条直接推翻了两个设计决定(原计划因此作废),记在这里免得后人照档案返工。

| # | 档案原话 | 实测结果 | 影响 |
|---|---|---|---|
| 1 | §1.2 / §3.1:«无 token **不带头仍会发请求**(是否被拒取决于服务端)» | 匿名即 `code=0`,且响应头带 **`access-control-allow-origin: *`** | **浏览器可直连,不需要同源转发函数** —— 原计划的 `functions/api/riftbound/userIntegral/…` 整个作废(与 `cardCommonQa` 的情况不同,那个端点确实缺 CORS 头) |
| 2 | §4.3:«**未观察到** `rankName`(榜单只给 `rankIcon` 图片,不给段位文字)» | **`rankName` 是返回的**,4 个段位名都是干净字符串 | **「按 rankIcon 反推段位名」的设计作废**。段位列直接显示服务端给的名称,零推断、零维护 |
| 3 | §3.2:«`pageSize` 硬编码常量 10» / §3.5:«翻页到第 100 页即停» | 那是**客户端小程序的行为**。服务端老实尊重 `pageSize`:实测 1000、5000 都足量返回 | **「100 页爬取」方案作废**。全量前 1000 名只需 5 个请求(每批 200) |
| 4 | `point-rank.wxml:21`:«仅展示**前 1000 名**的玩家» | 这也只是小程序的软上限。`pageNum=2` 实测**非空** | 「前 1000 名」**没有服务端依据** —— 界面文案因此不能说「你不在前 1000 名」,只能说「本次快照覆盖第 1–N 名」 |

顺带坐实的:信封比档案 §4.1 记的多 4 个字段(`resData` / `type` / `timestamp` / `traceId`);档案 §4.2 推断 `/info` 的 `result` 含 `id` 字段、§4.4 靠 `item.id` 判定「哪一行是我」——**与本工具无关**(只用 `ranking/list`),但那条推断至今未验证。

> **没有验证的**(本工具用不到,留给以后):`/userIntegral/info`、`/userIntegral/ranking/list/around`、`type=1/2` 的语义、榜单真实总量(探到 5000 行仍有数据就按站点要求停手了)。

## 3. 抓取口径

| 项 | 值 | 理由 |
|---|---|---|
| 单次 `pageSize` | **200 封顶** | 服务端能吃更大,但这是站点明确裁定的自我约束 |
| 首屏 | 1 个请求 = 200 行 | 秒开;这 200 行同时也是无限滚动的第一批 |
| 追加 | 无限滚动,每批 200 行 | 滚到底部触发,追加下一批 |
| 翻页护栏 | `MAX_PAGES = 50`(10000 行) | 防的是「谁滚到底就一直翻」把上游当自家数据库刷 |
| 到底判据 | 某页不足 200 行 | |
| 请求间隔 | 300 ms + 指数退避重试(3 次) | 官方接口在持续快速请求后会触发 WAF 限流,见 `src/tools/sync/riftboundApi.ts` 的注释 |
| 重试范围 | 网络错误与 5xx / 429;**4xx 不重试** | 4xx 是确定性拒绝 |
| 快照存放 | 仅 `localStorage`(`riftbound.rankLadder.snapshot.v1`) | 不做服务端缓存,站点不发布榜单副本 |
| 刷新策略 | **纯手动**,本批失败即作废(丢弃半份、不写缓存、游标不动) | 站点裁定 |

**快照按 uid 并集追加,不重排。** 上游在两次请求之间会推进名次,新页里可能出现与已抓行同 uid 的新行;保留先到者则整表稳定,代价是新页中重复 uid 的新名次被丢弃 —— 需要精确最新值时由用户显式「重新抓取」重建。

## 4. 实现时踩过并已修掉的缺陷

这几条都写进了 `scripts/verify-rank.mjs` 的断言,别退回:

| 缺陷 | 症状 | 根因 |
|---|---|---|
| **无限滚动级联刷上游** | 一次滚到底连抓 6 批(200 → 1400 行,游标到第 8 页) | 曾在 `canLoadMore` 变化时重新 `observe()` 哨兵。而 `observe()` 会**立刻**用当前交叉状态回调一次,加载完一页后哨兵若仍在视野内就自我触发成级联。现在只 observe 一次,靠交叉状态**变化**触发 |
| **无限滚动根本触发不了** | 滚到底毫无反应,停在 200 行 | 表格曾套 `max-h-[70vh]`,200 行全在容器内部滚动(实测容器 `scrollHeight` 9033px 而文档只有 1239px),页面不滚动,哨兵永远卡在容器下方。内层滚动区与无限滚动天生打架,现已去掉 max-height |
| **排序假象**(功能已按站点要求移除) | 表头箭头变成 ↓,行序纹丝不动 | 模板错取了 `filteredRankRows`(只筛未排)。这条催生了「DOM 行序必须逐行等于 store 计算值」的断言,保留至今 |
| **界面态跨页面泄漏** | 离开再回来,上一轮的筛选还留着而搜索框是空的 | `rankState` 是模块级单例,挂载时未重置选择态。现在挂载即 `resetUiState()`(快照要留,选择态不留) |
| **重抓期间闪空白** | 点「重新抓取」时表格清空一两秒 | `resyncRank()` 先把快照置空。现在重建期间保留上一份渲染结果,失败还会**还原**旧快照并如实报错 |
| **挂载即自动抓一批** | 从底部滚动的页面跳进来,什么都没点就发请求 | hash 跳转与浏览器恢复滚动位置都不会归零,哨兵挂载即可见。现在挂载即 `scrollTo(0, 0)` |

## 5. 有意的取舍

- **不提供排序。** 榜单顺序即官方名次顺序。让人按积分或昵称重排只会诱导误读 —— 名次是并列跳号的,重排后名次列会显得毫无规律。表头因此不可点、不可聚焦;`store` 里也没有任何排序态(`A11c`/`B6i` 断言守着这条)。
- **不调 `/userIntegral/info`,不调 `/ranking/list/around`。** 站点裁定不要 token、只看排名。`/info` 与 `/around` 的锚点是登录态自身,既拿不到也不需要。段位进度、段位分享卡这些都无从实现,也不该假装能实现。
- **段位筛选选项从已抓数据动态生成**,不硬编码段位名 —— 上游将来新增段位时选项自动跟上。
- **榜外玩家必须如实归因。** 搜不到时说的是「已抓取的 N 行里没有匹配」+「本次快照只覆盖到第 N 名」+ 提供继续抓取与重抓入口,**不谎称「该玩家不存在」**。
- **不做跨数据关联。** 榜单玩家与赛事数据包里的参赛者昵称匹配这件事没做,也没留钩子。

## 6. 验收

```bash
npm run verify:rank     # 已包含在 npm run verify:all 里
```

两段各管各的失守方式:

- **A 段(离线,50 项)**:参数护栏必在发请求前拒掉、并集追加语义、覆盖范围取最大名次、段位选项动态生成、筛选保持名次顺序、无 `localStorage` 时不崩、登记口径。
- **B 段(联调,50 项)**:CDP 驱动 headless chromium 打开 `#/rank`,用**真实上游请求**跑通首屏 200 行 → 搜索 → 段位筛选 → 名次顺序 → 无限滚动 → 刷新恢复 → 重新抓取。含两条网络层断言:**一次滚动只发一个上游请求**(防级联)、请求体确为 `pageNum=N` / `pageSize=200`。

脚本自管 `vite preview`(4173 已被占用则复用、退出不误杀)。截图输出到 `shots/rank/`(已 gitignore)。

```bash
npm run build:fast && npm run verify:rank
```

> B 段依赖真实网络。抓不到上游时它会失败 —— 这是刻意的,接口契约本身就是被测对象。
